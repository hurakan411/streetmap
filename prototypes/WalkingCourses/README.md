# Walking course proposal MVP

Source checkpoint before this feature: `21dfb853d2ab6d008c0519f691232b3ac2789e47` on `hurakan411/streetmap`.

## Behavior

### Walking / cycling selection

The shared conditions bar contains Starting point / Mode / Duration in that order, followed by the search end-cap. All three fields use the same label/value typography, chevron, 62pt height and padding; Mode is not a separate pill above the bar. Its menu chooses Walking or Cycling, defaulting to Walking. It is independent of recording/capture settings and historical visibility filters. Changing mode cancels the current request, clears its stale candidates and preserves start/duration/direction. Labels, origin symbols, seed search distance, MapKit transport type, cache keys and novelty-history mode follow the selection. Search radius seeds use 1.15m/s walking or 3.9m/s cycling; the displayed ETA uses the actual returned MapKit estimate, not that seed speed. Saved proposals carry an optional `travelMode`; old files without it restore as Walking. There is no change to real movement records.

The displayed direction circle/sector now uses its real geographic radius, not the old 90–145pt size clamp: 30 minutes gives 345m for walking or 1,170m for cycling (about 3.39×); doubling time doubles radius. It is an indicative loop radius, not an isochrone or guarantee that every point is reachable. Only the drag handles keep screen-space size/position limits. On a radius/start change the map zooms out if necessary to fit the circle above the controls; normal pan/zoom never triggers automatic reframing. Switching back to a smaller circle does not force a zoom change.

Cycling explicitly requests `MKDirectionsTransportType.cycling` (Apple's official API). The old primary-transport equality check was removed after an iOS 26.5 comparison at public Shinjuku station locations: an explicit cycling request returned overall type 1 with mixed type 1/2 steps, but different geometry/ETA and cycling notices compared with the automobile request. The equality check wrongly discarded these cycling responses. Request mode and the mode-separated cache are now the provenance; production cycling code never requests automobile directions as a fallback. Responses marked as containing highways are conservatively excluded. Apple's advisories (shared/main roads, possible pushing sections, etc.) are retained with the course and displayed on cycling cards; this is not turn-by-turn guidance or a guarantee of access/safety. An iOS-only temporary probe compiled the production engine against empty synthetic history and returned a 6,549m / approximately 31-minute cycling loop with 0.3% repeated geometry. Candidate availability still depends on the local network and bounded search. Menu-touch/physical-device cycling results are not yet claimed verified. Offline tests cover mode-change cancellation, old/new saved-file compatibility and cycling advisory persistence.

- The new button immediately below Settings opens planning on the existing map.
- Start defaults to a location already available to the app. Change it with location search, the current-location action or a map long press. No location permission is required for a manually selected start.
- Conditions sit immediately above the compact results card: start, 20/30/60-minute duration and the orange search button. Planning hides all right-side buttons except the course toggle.
- The conditions use one frosted-material bar: two labeled selectors and an attached orange search end-cap. The result card uses the same material with opaque text, aligned metrics and 44pt navigation targets. Both adapt to the theme and become solid when Reduce Transparency is enabled. Native material is used instead of capturing/processing map images during gestures. Planning-only map attribution/button spacing reserves room for the taller result state; normal map controls are unchanged.
- A translucent sector is anchored to the start. The default is a full 360-degree circle. Drag the center handle to rotate it, or either side handle to set its opening from 0 to 360 degrees. Width dragging accumulates signed rotation across the wraparound seam. Only handles intercept touches; other touches remain map pan/pinch gestures. The handles stay usable at different zooms, track geographic bearing and rotate with the map. Drag updates stay local until release to avoid rebuilding the map each frame.
- The map-mode button uses a stable layers icon. Tap cycles full map → reveal walked areas → routes only → full map. Long press provides the same ordered list with the current mode checked.
- Changing conditions cancels stale requests and removes stale candidates; search again to generate new candidates. A sector narrower than eight degrees shows a request to widen it, because a useful round trip cannot be generated in an almost-zero-width sector.
- A compact floating card contains only candidate numbering, walking ETA, total distance, estimated unrecorded walking distance and up to two actual nearby place names. There is no course name, details action or color legend.
- All proposed paths are orange with a white halo. Existing history retains its theme color and remains on its original persistent renderer. Switching candidates replaces only the temporary course overlay and annotations. Closing restores the prior map mode.
- Proposed/saved courses stay in front of recorded and live route strokes, including when an asynchronously prepared history surface is registered later. The coordinator promotes only the proposal through adjacent same-level overlay exchanges, preserving other overlays' relative order without removing/recreating the proposal or restarting animation. Registration of history/live/mask renderers and ordinary course updates all recheck this invariant.

- Named course-stop pins now enter the place-detail flow instead of falling through to the background UI toggle. A bounded local search resolves an equal normalized name within 80m, then presents the existing compact Apple place card on iOS 18+. If no verified item is found, the existing basic place sheet shows the saved name/coordinate without substituting an unrelated business. Selection/dismissal cancels stale lookups; in-flight lookups suppress the same tap's background action. The start indicator is not selectable. Ordinary Apple POI selection still respects its visibility setting and the revealed-area mask; course-pin resolution does not change that setting. Simulator and device Release builds pass; post-fix modal visual confirmation is pending a renewed Mac unlock.

## Generation and limits

The engine is an actor. It uses eight seed variants plus at most two overlap-corridor repairs, requesting three legs in the selected travel mode per trial from `MKDirections`. A rejected loop records the direction/location of its longest internal repeated corridor. The nearest waypoint is moved perpendicular to that corridor by 65–280m (scaled to route length), constrained to the chosen sector, and all three legs are routed again by Apple. At most ten trials / thirty leg requests occur, stopping early once three distinct loops close to the requested duration exist. At 360 degrees the seeds explore eight compass regions; narrower searches keep their waypoints inside the sector. The waypoint span is capped at 120 degrees. It requests alternatives and prefers legs avoiding the already assembled part; alternatives above 1.8× the fastest leg ETA are excluded. The bounded cache stores mode-separated alternatives. Radius adaptation is damped with a square root to avoid oscillation between short and long seeds; repair trials do not distort that calibration. Directions are paced and cancelled after 18 seconds, optional POI queries after eight. Closing/changing conditions cancels work, and a later throttle/server failure preserves valid earlier candidates.

Before loop rejection, short waypoint-induced dead ends are pruned only where an exactly identical coordinate is revisited. Removed excursions must enclose less than 50m², be at most 300m each and total at most 20% of the original route. Start and finish are preserved, no new road segment is invented, and distance/ETA are reduced in proportion to retained geometry. The unchanged strict loop gate is then applied. Large out-and-back routes are not accepted as a fallback.

No straight-line replacement route is fabricated. Candidate legs must meet within 35m, return within 35m of their start, and start within 80m of the requested location. Candidates within 50–170% of requested time remain usable; those within 75–130% are ranked ahead of out-of-band alternatives, and the actual route ETA is always displayed. Within each band, novelty, direction, time fit and repeat penalty determine rank. At least 60% of sampled route length outside an 80m start corridor must follow the sector with eight degrees of tolerance. Spatially near-identical candidates are removed. Up to three candidates are returned; none is still possible where no acceptable loop can be found. This samples the road network, not a globally optimal solver or reachability guarantee.

Loop quality samples geometry at ≤10m, compares headings/proximity within 6m, and ignores adjacent samples ≤35m along the path. Reused distance counted in both directions is capped at 12% in both modes. Walking retains its 30–80m longest-repeat allowance and 12m internal-repeat limit. Cycling scales longest-repeat allowance to 3% of total (45–180m) and internal reused length to 3% (18–180m): a small junction overlap no longer discards a multi-km ride. Both still require closure ≤35m, area ≥2,000m² and area/perimeter² ≥0.004. Long stems, large internal spurs, thin return corridors and pure out-and-backs remain rejected; failed corridor candidates may trigger the bounded waypoint repair above. This is a geometric estimate, not road-ID identity. Direction, duration and highway constraints are not bypassed by repairs.

Planning opens at a 900m span instead of a fixed 2km span. Fitting a candidate uses only a small additional inset; the planning layout margins already reserve the card/attribution area. Normal map/retained-course camera padding is unchanged.

All-date accepted raw walking legs from `RecordedDistanceCalculator` form a local spatial index. Estimated tracks, transport legs and invalid measurements are excluded. The route is sampled at approximately 12m; a recorded segment within 20m and similar heading marks that portion as already walked. This is an estimate, not road-ID identity, and cannot know walks not recorded by the app. Date/transport **visibility** filters do not change novelty. History processing is off the UI actor, and raw history is not submitted to Apple. Only the selected start, generated waypoint locations and POI search regions are used in requests.

POIs within 90m of the path are optional nearby suggestions, not guaranteed directly reachable entrances or mandatory stops. Park category filtering excludes parking; shrine/bookstore name validation rejects unrelated search results. No made-up attraction fallback is shown. Hours, access restrictions, safety, scenery and navigation are not verified. ETA excludes stops. There is no turn-by-turn guidance in this MVP.

## Verification

2026-10-24 adaptive-search verification uses the production engine in an isolated iOS 26.5 probe, with empty synthetic history and public station locations. Shinjuku / cycling / 30 minutes returned three loops (about 28, 30 and 32 minutes); Ueno / cycling / 20 minutes returned three alternatives (18, 25 and 33 minutes), with the preferred-duration alternatives ordered first. In Ueno the initial overlapping corridor was repaired into a valid alternative by moving a waypoint and rerouting. The 33-minute result is explicitly an out-of-band alternative, not a claim of a 20-minute ride. All returned paths passed the cycling loop policy. Tests do not establish availability at every start or legal access/safety of every road.

Offline regressions cover a small overlap in a 6km ride, rejection of large repeated stems/spurs, repair-point direction constraints, changes affecting only the nearest waypoint, duration fallback/preference limits, plus all earlier geometry and 31 saved-course assertions. A Shinjuku walking / 30-minute iOS probe also recovered a valid approximately 30-minute circuit after corridor repair; a later MapKit service error retained that already collected candidate. iOS device/simulator Release builds pass. No actual user history was changed during these tests. The temporary probe app was removed and its simulator restored to shutdown afterward.
